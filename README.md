# OAuth App Guides

Look up an app and find out what it takes to get its OAuth app ready: the steps, the time, the approval wait, the blockers, and what an agent can do for you. If an app isn't in the library, an agent investigates it live and publishes a shareable guide.

Built as a take-home for Composio's APM (toolkits) role.

## The problem as I understood it

Creating an OAuth app usually takes minutes, and Composio already has how-to pages for getting credentials. What a developer can't see is the distance between "it works for me" and "any customer can connect". Spotify is a clear example: the app takes minutes to create, but new apps stop at 5 users, and going further needs a registered business with 250k monthly active users.

So each guide is built around that ladder, and it opens with whatever is most likely to change the developer's plan.

## Key decisions

- **Start with "do you need this at all?"** Every guide first checks a snapshot of Composio's directory (125 managed toolkits, 262 bring-your-own). On a managed toolkit, the developer may be able to skip all of it.
- **Show who can connect at each stage.** Time estimates alone hide the real question, which is how far up the ladder a product has to go. Notion needs no review at all, whereas Slack lets anyone install but throttles message history until Marketplace approval.
- **Separate hands-on time from waiting.** They need different planning, and only one of them can be reduced by working harder.
- **Label every claim, and check the labels in code.** Claims are Tested (a live probe saw it), Sourced (a page the agent retrieved says it) or Uncertain. After each run, `src/lib/audit.ts` compares the labels with the server's own record. A "tested" claim must cite a probe that ran, and a "sourced" claim must cite a page that was retrieved. Failures are downgraded publicly on the guide.
- **Make the agent attempt things, within limits.** `probe_url` makes real anonymous requests: loading the registration page, reading OAuth discovery documents, and calling the authorize URL with a fake client ID. Creating accounts and passing review stay out of scope.
- **Say what an agent can't do.** Steps are marked Agent, You or Provider, because legal terms, identity checks, payment and security assessments need a person.

## What the verification changed

I checked 14 claims in a separate pass by fetching the provider's pages directly. The log is at `/evidence`.

- **10 confirmed.**
- **2 corrected, both on Spotify.** The agent reported one Client ID per developer from a February 2026 post, but a July 2026 update raised it to 25. It had also labelled a six-week figure uncertain when Spotify's docs state it directly.
- **2 could not be verified:** Shopify's real review time, and the logged-in flows in general.

The first correction changed the product: the agent is now told to look for changelogs from the past year, since a newer post overrides an older doc. Two runs on Spotify also disagreed on that fact, so a single run shouldn't be trusted for a guide that people will plan around.

## How it works

- `src/lib/agent.ts`: a Claude agent loop with web search, web fetch, `probe_url` and `submit_guide`. Output is validated against the Zod schema in `src/lib/schema.ts`, and invalid guides go back to the agent to fix.
- `src/lib/probe.ts`: the anonymous request tool. The model chooses the URLs, so it allows public https hosts only, re-checks each redirect, and caps time and size.
- `src/lib/jobs.ts` and `netlify/functions/generate-background.mts`: a run takes 1-3 minutes, which is longer than a normal function can stay open. The API route queues a job, a Netlify background function runs it, progress is saved to Netlify Blobs, and the page polls every 2 seconds. Refreshing rejoins the same run, and two people entering the same app share one.
- `src/data/guides/`: the library, generated by the same agent and committed.

## Run it locally

```bash
npm install
cp .env.example .env.local   # then add your ANTHROPIC_API_KEY
npm run dev
```

Live guides are stored in `.data/` locally. To regenerate library guides:

```bash
npx tsx --env-file=.env.local scripts/generate-library.ts Notion Slack
```

## Deploy on Netlify

Import the repo and add `ANTHROPIC_API_KEY` as an environment variable. `netlify.toml` covers the build, and Netlify Blobs needs no setup. Set the key before the first live run: without it, Netlify's AI Gateway supplies its own, and each run uses up your Netlify credits.

## Limitations

- **Six guides, not 100.** The brief asked for a few varied apps. Generating more is a matter of running the script, but quality at that scale would need a review process.
- **Nobody completed a real setup.** No provider accounts were created and no apps were submitted. Probes only show what an anonymous visitor sees, and pages rendered with JavaScript are flagged as inconclusive.
- **Review times are often estimates.** Few providers publish them, so those figures rest on forum reports and are labelled Uncertain.
- **Guides go stale.** Each shows its date, but nothing regenerates them. A scheduled re-run that flags changes would be my next step.
- **Directory matching is exact, on a snapshot.** An app listed under a different name shows as "not listed".
- **Rate limits are simple.** Live generation allows 40 guides a day and 6 per visitor, stored in Blobs without atomic updates, so a burst can overshoot slightly. The probe's address check can't fully stop DNS rebinding.
- **Corrections are manual.** The Spotify fixes were made by hand and would be overwritten by regenerating that guide.
